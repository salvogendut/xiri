# NetBSD disk and network qualification — 2026-10-30

Repeated disk writes, checksum checks after a cold start, and bidirectional
network transfers passed in CI and ordinary execution. This extends the
[debugger and smoke tests](2026-10-30-netbsd-debugger-probe.md). Results are
limited to the installed R4400 guest and the recorded workloads.

## Emulator change and reproducibility

Emulator development now lives in the user's [IRIS fork](https://github.com/salvogendut/iris/tree/d6420795a00f139cd0f638a623c55a071b46e9e9),
branch `xiri/netbsd-io`. Commit
`d6420795a00f139cd0f638a623c55a071b46e9e9` starts from the previous Xiri
baseline `b188bb9a82842948ddf2534f07d718df8473942c` and changes NFS MOUNT
authentication negotiation. The fork's newer `main` includes separate device
refactoring and was not used in these tests.

The initial UDP NFS attempt on the unmodified emulator returned
`mount_nfs: can't access /: Authentication error`. NetBSD 11.0's
`sbin/mount_nfs/getnfsargs.c:xdr_fh` requires the requested AUTH_UNIX flavor
when MOUNT v3 supplies a nonempty list. IRIS advertised only AUTH_NULL even
though its RPC parser already accepts UNIX credentials. The fix advertises
AUTH_SYS (the same numeric flavor as AUTH_UNIX) and retains AUTH_NULL.
This changes negotiation; the export still uses synthetic ownership and
permissions rather than authenticating those credentials.

NetBSD also needs `mount_nfs -3 -u -U`: IRIS's built-in server implements UDP,
while NetBSD defaults to TCP. Both requirements are documented in the fork's
`HELP.md`. The existing MOUNT wire test now checks both advertised flavors;
all 21 `net::nfsudp::tests` passed with the modified source.

Build with `IRIS_SOURCE_DIR=../iris ./scripts/build-iris.sh`. The normal build
also fetches the pinned fork commit into Xiri's managed `.work/iris` checkout.
The Rust nightly, dependency lockfile, and default features are unchanged.
The release build succeeded with the existing REX3 deprecation warning.

## Workload

The [I/O harness](../../scripts/qualify-netbsd-io.py) reuses the existing boot,
serial, timeout, and cleanup code. Each run uses a disposable copy of the stopped
custom-kernel checkpoint, independent ports and logs, and generated media.
Ordinary mode keeps Newport enabled and places the host window on Xvfb.

The [disk script](../../lab/indy-netbsd/disk-probe.sh) copies two distinct 16 MiB
files from CD, syncs, and compares SHA-256 hashes. Three rounds alternate which
payload overwrites each destination: 96 MiB written and checksummed. After
clean shutdown, a fresh emulator process boots the same disk and verifies both
files again (32 MiB), including a clean root-filesystem report at startup.

Network tests download and upload 16 MiB through NFSv3/UDP, download 16 MiB
through HTTP three times, then upload 16 MiB over TCP. Every destination is
checked against the host-generated hash. This totals 96 MiB of network payload
per run, excluding boot traffic. The NFS export and loopback HTTP/TCP services
contain only disposable test data. The test mount uses soft retries so a failed
server does not indefinitely block cleanup.

The commands are documented in the [guest lab](../../lab/indy-netbsd/README.md#disk-and-network-qualification).
Full serial, monitor, emulator, and HTTP logs and `result.json` remain under
`.work/netbsd-io/`. The run records include input and harness hashes, completed
guest exit statuses, elapsed host time, and clean-shutdown outcomes.

## Earlier installer failure

Before changing the emulator, a fresh installed guest downloaded and checked
1 MiB and 16 MiB successfully over HTTP. The 16 MiB file's host and guest hash
was `69d1fa0fb48137a301bd61eb9c3a632736a266d15917a6aeaf2e640067f344b2`.
The earlier installer transfer that stalled around 6.4 MiB was therefore not
reproduced by that experiment. Its cause remains open: the NFS change does
not modify TCP or Ethernet DMA. Evidence for this investigation is retained
in `.work/netbsd-io-investigate/`.

## Scope

These are bounded integrity tests, not a disk endurance or network performance
benchmark. Some runs overlap on the host. Power-loss recovery, restored RAM
snapshots, the installer's larger HTTP path, R5000 cache handling, entropy,
host device-probing diagnostics, guest X, MAME comparison, and physical
hardware remain separate work.

The CI network run completed despite TCP retransmissions: 706 data packets
were retransmitted and 33 retransmit timeouts occurred, with no connections
dropped by retransmit timeout or bad TCP checksums. `sq0` reported no input or
output errors or drops. NFS reported nine retries and zero RPC timeouts.
The ordinary run recorded 369 retransmitted data packets, 14 retransmit
timeouts, and ten NFS retries, also with zero interface errors, bad TCP
checksums, RPC timeouts, or connections dropped by retransmit timeout.
These counters are retained for future throughput work; checksum success
does not establish loss-free transport or explain the earlier installer stall.
