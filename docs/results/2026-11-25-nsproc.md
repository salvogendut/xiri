# Vendor pthread workers and the two Mozilla launchers

Both original-media Indy desktops now pass the SGI libpthread create/join test
with NetBSD `xiri` commit `6fd0cea0f77`. Both catalog icons start the vendor
browser and create workers. A usable Navigator window and local page remain
open on both releases. [Machine records, checksums and traces](2026-11-25-nsproc.json).

## What passed

| Test | IRIX 6.5.22f on Xiri Indy R4400 | IRIX 6.5.30f on Xiri Indy R5000 |
| --- | --- | --- |
| Raw n32 child registers and fixed-address private data | 25 words match original IRIX | 25 words match original IRIX |
| Default scope as xiritest and as root | Worker wrote 42, join returned its address | Same |
| Five additional default-scope runs as xiritest | 5/5 | 5/5 |
| System scope as root | Worker and join passed, native round-robin | Same |
| System scope as xiritest | SGI library returned EPERM at attribute selection | Same |
| Native shell child status and X session | Status 17 returned, 4Dwm and Icon Catalog present | Same |

The raw control ran on original IRIX 6.5.22f on an Indy and 6.5.30f on an
O2. The parent received thread ID 1. The child entered the syscall trampoline
with the descriptor argument in a0 and its stack pointer 64 bytes below the
aligned top. The child inherited a PRDA marker, then changed its private copy.
The parent retained the original marker. The two threads had the same process
ID. Root's explicit system-scope call requested policy 2 and priority 0 on
both Xiri systems. [Fixture source and reproduction](../../lab/irix-pthread/README.md).

The module creates detached NetBSD LWPs. On a uniprocessor, a scheduler hook
switches the 4 KiB IRIX PRDA at its fixed virtual address when a different
worker of the same process runs. The adapter handles worker exit, interruptible
block and counted unblock. The first successful worker pins its PRDA window
until exec or exit. The existing single-thread restrictions on operations such
as fork and ELF mapping still apply. Multiprocessor kernels reject hook
registration. [NetBSD core changes](../NETBSD-UPSTREAM.md#required-core-interfaces).

## What happened when we double-clicked

We logged in through xdm as xiritest, opened Applications and used XTEST to
double-click each original icon. We traced the live catalog process and its
descendants and recorded the browser PID, worker returns and X window tree.
On the disposable copies, a Mozilla default preference pointed to a local
page titled **Xiri local thread test**. We also opened its file URL explicitly
through the SGI shell launcher.

| Release and browser | Both catalog icons | Explicit local URL |
| --- | --- | --- |
| 6.5.22f, Mozilla 1.0.1 | Each started a distinct browser PID. Each trace recorded worker IDs 1 and 2. The browser continued consuming CPU without displaying Navigator. | The browser was still running at the 55-second timeout. It reported failed mappings for `libucvibm.so` and `libucvko.so`. |
| 6.5.30f, Mozilla 1.7.12 | Both created worker 1, then called exit with status 1. A 10×10 startup window appeared briefly. | The launcher returned 1 in two runs. The page title never appeared. |

On **6.5.22f**, both converter libraries exist on disk. Each has a writable
load segment below its executable segment, and the program headers list the
writable segment first. The current SGI_ELFMAP adapter expects executable
text first and data above it. Both catalog traces associate those libraries with ENOEXEC before worker
creation. The direct trace also recorded two such failures. These are confirmed loader gaps. Whether correcting
them suffices to display Navigator needs a new run.

On **6.5.30f**, both catalog traces identify
`/var/netscape/mozilla/components/libnsappshell.so` immediately before an
SGI_ELFMAP return of IRIX EOPNOTSUPP (122). The direct trace recorded 33
successful ELF mappings before worker creation and this rejection afterward.
The kernel currently requires a single unshared map for multi-segment
rollback. The next focused regression is to load a two-segment library with
a worker alive and verify that failure leaves existing mappings intact.
The GTK shared-memory warning occurred earlier in startup on both lines.

## Rebuilding the tested Indy pair

Use NetBSD `xiri` at `6fd0cea0f77`, the existing sgimips cross tools and a
fresh output directory. From the Xiri checkout, run the following commands.

```sh
sh lab/ip28-kernel/build.sh ../NetBSD-xiri "$tools" "$out" "$PWD/lab/irix-module/XIRI_IRIX_MODULE"
sh lab/ip28-kernel/build-module.sh ../NetBSD-xiri "$tools" "$out"
```

On a private v5 Indy copy with the release-matched browser payload, install
`kernel/netbsd` as `/netbsd`, `kernel/netbsd.elf32` as `/netbsd.boot`, and
`module/compat_irix_o32.kmod` in
`/stand/sgimips/11.99.11/modules/compat_irix_o32/`. Cold boot before testing.
The lab retains the tested pair in
`.work/modules/irix-nsproc-20261125/indy-kernel-module.tar.xz`.
The kernel resolved all 206 module imports and loaded the module at securelevel 1
on both guests. The 96 host tests passed. Qualification used private overlays.
The v5 CHDs, NVRAM and emulator hashes still match their manifests.
[Browser payload instructions](2026-11-24-indy-mozilla.md#build-the-matching-payload).
