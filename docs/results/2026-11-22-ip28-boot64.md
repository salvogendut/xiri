# IP28 BSD bootloader, 2026-11-22

A working ELF64 BSD bootloader is available for Indigo2 IP28/R10000.
It boots from the SGI disk volume header, reads FFS, loads an ELF64 payload,
passes NetBSD boot information and returns cleanly to the PROM. This removes
the PROM's `Unknown ELF class 1` rejection of the existing ELF32 `boot` file.

It does **not** boot the full Xiri system yet. Both maintained Xiri images
contain Indy-linked kernels; neither is an IP28 kernel. They are preserved
as the qualified Indy desktop artifacts.

## Source and changes

NetBSD commit
[`b84b5316b3a`](https://github.com/salvogendut/NetBSD-xiri/commit/b84b5316b3a4c55d8fbc986aecac24601a0e7f2d)
is integrated into `xiri`. Development used the isolated
`topic/sgimips-ip28-boot64` worktree based on `93a25807724`, preserving the
separate Octane topic checkout and existing pinned lab trees.

The implementation repairs the existing standalone `boot64` path:

- `stand/boot64/Makefile`: select N64 startup and ARCS64 calls; build
  `ip28boot` at `0xa800000020003000`; keep the ELF load segment at that
  exact address, above firmware-reserved pages.
- `stand/common/start64.S`: preserve N64 arguments and stack state, initialize
  BSS and the 64-bit firmware vector, and return through the firmware's
  interactive-mode service.
- `dev/arcbios/arcbios_calls.S`: use 64-bit vector entries and slot spacing
  for the standalone ARCS64 build. The existing kernel bridge is unchanged.
- `dev/arcbios/arcbios.h` and `stand/common/disk.c`: use the IP28 PROM's
  16-byte seek-position layout. Each high/low 32-bit half occupies a 64-bit
  firmware long. The old layout returned successful seeks but failed disk
  reads; the corrected layout passes on the fixture and both Xiri disks.
- `stand/common/boot.c`: handle a single PROM argument safely, check the
  kernel's destination against ARCS64 usable RAM before loading, and flush
  caches before entry. The address check applies only to ARCS64.

The bootstrap and kernel addresses are already documented in NetBSD's
`sys/arch/sgimips/README.IPn`. This work uses the existing NetBSD source,
public firmware interfaces and observations from the supplied PROM.

## Validation

The machine is IP28/R10000, 1 GiB RAM, High IMPACT, with the embedded PROM
and the November 22 accelerated IRIS binary. The loader checks use a serial
PROM console with a visible emulator window.

| Check | Result |
| --- | --- |
| IP28 ELF64 loader build | Passed, entry `0xa800000020003000` |
| Legacy `ip2xboot` and `ip3xboot` builds | Passed; no runtime regression claim |
| Historical `ip30boot` target | Builds; runtime and its existing load address remain unqualified |
| TFTP bootstrap → FFS payload | Handoff passed; returned to PROM |
| Disk volume header → FFS payload | Handoff passed; returned to PROM |
| Packaged CHD checksum and independent boot | Passed; handoff passed and returned to PROM |
| Xiri with IRIX 6.5.22f resources | Read kernel headers, rejected Indy address range, returned to PROM |
| Xiri with IRIX 6.5.30f resources | Same expected rejection; returned to PROM |

The source-built payload checks data, BSS contents, argument pointers,
bootinfo magic, boot path and symbol information. It has no vendor files.
The [JSON record](2026-11-22-ip28-boot64.json) retains the exact serial results,
binary hashes and source revisions. The
[build and check instructions](../../lab/ip28-boot64/README.md) reproduce
these tests. Local logs are in `.work/indigo2-netbsd-20261122/`.

IRIS upstream was checked at `6ec1ebf379228d572026a9ae8d291511ed28af74`;
there were no incoming commits beyond the current integration. The fork
remains at `eb21c6ec`, whose only change from the tested `0bc52567` binary
is the previously documented IMPACT regression-test correction.

## Retained artifact and next step

The local bundle is `.work/native/netbsd-ip28-loader-20261122/`:

- `ip28boot`: 70,312-byte standalone loader;
  SHA-256 `8ca708961921510268bb0cbc718aed4e4e112ebdb7f558b764c6c2a0b1e220da`.
- `loader-test.chd`: 33,862-byte compressed, vendor-free test disk
  (32 MiB logically), containing the loader as `boot` and the handoff probe.
- `xiri-ip28-probe` and `qualification.json`: the payload and recorded checks.

The firmware settings remain BSD settings: `OSLoader=boot`, with the kernel
name in `OSLoadFilename`. The original Xiri disks were already configured
that way; their loader's ELF class was the first problem.

With the new loader, both disks report:

```text
Kernel address range 0xffffffff88060000..0xffffffff8874e838 is outside usable firmware RAM.
Use a kernel linked for this machine.
```

IP28 RAM begins at physical `0x20000000`, while these kernels target Indy
RAM around `0x08000000`. Relinking alone is insufficient: the next cycle
needs native IP28 kernel support, starting with the ARCS64 handoff, memory
and CPU initialization, then console, interrupts and storage. IMPACT display
and Xorg support follow a successful native NetBSD boot. This is separate
from the working native IRIX 6.5.22f desktop.

Temporary build trees, disk copies and test overlays are removed after saving
the result. The small loader bundle, source, logs and both qualified Xiri
release artifacts remain available; all test IRIS instances are stopped.
The completed topic worktree and branch were removed after the integration
push, and the build container was stopped. Cleanup removed 1.07 GiB of
allocated temporary files; measured filesystem free space increased by
210 MiB. Shared reflink blocks, compression and concurrent activity make
those figures differ. The retained loader bundle occupies about 144 KiB,
with about 2.9 MiB of local build and test evidence.
