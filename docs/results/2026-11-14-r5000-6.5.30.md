# Indy/R5000 boot and IRIX 6.5.30

The existing NetBSD Indy kernel boots on R5000 with IRIS `xiri` commit
`7d46498bf1fbf3acf53f1619413e3c5eaeb5d27b`. It reaches native serial login and
the full-screen xdm greeter. With the updated compatibility module and IRIS
**shadow cache mode**, the original-media **6.5.30f core desktop checks pass**.
The shared module also passes the separate **6.5.22f/R4400** regression.
No native kernel replacement is needed. The selected 6.5.22m manual CHD
remains unchanged. The subsequent [manual previews](2026-11-15-irix-previews.md)
package both tested disk states as standalone CHDs with pinned launchers.

The [machine-readable summary](2026-11-14-r5000-6.5.30.json) records both
release results, source/build pins, interruptions, limitations and cleanup.

## Native boot correction

The earlier `panic: r5k picache line size 16` came from the emulator allowing
software to clear the R5000's fixed Config IB/DB bits. The correction preserves
those bits on R5000 and keeps R4400 behavior unchanged. Its MTC0 regression
failed before the correction; all 190 executor tests and the optimized build
passed afterward. See the [original investigation](2026-11-14-irix-6.5.30.md).

The new cold boot uses Indy/IP24, R5000 revision 1.0, 256 MB RAM and Newport.
NetBSD reports 32 KB, 32-byte-line, two-way primary instruction and data caches.
The existing kernel hash is
`c92f0b2fcc182836393a87ca41a0315a0681e93ed3e904fad925d3c370e4dd98`.
The test verifies that kernel and the inherited native file ledger before
changing the vendor payload. The serial login follows graphical startup;
the initial silent serial connection was not another boot failure.

## Separate vendor release

This experiment runs **6.5.30f applications on NetBSD**, using files imported
from the separately qualified original-media O2 donor. It does not boot an
IRIX 6.5.30 kernel on an Indy. The donor's MIPS IV libraries require a suitable
CPU, which R5000 supplies. Native O2 and Octane support remain separate work.

The disposable test removes the old vendor tree and imported fonts completely,
then uses native `pax -rz -pe` to extract the pinned 6.5.30 payload. Every
imported regular file must pass its hash check before desktop startup.
The existing 6.5.22 manual CHD, donors and payloads remain separate.

## Full-cache import failure

The first run uses the interpreter's default `full` cache model. Native boot,
kernel/native file hashes and payload extraction pass, but vendor verification
fails before any 6.5.30 program runs. The loader `/emul/irix/lib/rld` itself
matches its expected hash. The guest halts cleanly with the source CHD unchanged.

A cold boot of that halted disk confirms persistent differences. Three reads
of n32 libc and the `Scr10.pcf.Z` font produce the same incorrect hashes. The
4,859-byte font is also transferred to the host and compared directly against
the archive: 525 bytes differ, in 17 aligned 32-byte blocks whose installed
contents are all zero. The host agrees with the guest's font hash, so this
sample is a data discrepancy, not just a checksum calculation error. The
verification log itself contains zeroed blocks and at least 73 failed-file
lines. Those observations do not yet identify whether the cause is in the
full cache model or NetBSD's use of it.

Streaming that one font from the same CD archive with `tar -xOzf` into a
separate file produces its expected hash. The source archive therefore supplies
the correct bytes in this control. The diagnostic guest was then deliberately
interrupted through the probe's cleanup handler and halted cleanly; its result
retains the interruption rather than claiming a passing desktop test.

The maintained probe now accepts `--cache auto|full|shadow` for an explicit
comparison and records that choice. Failure collection uses `grep -a` so zero
bytes in a damaged log do not hide every failed filename behind a generic
"binary file matches" message. The `shadow` comparison starts from a fresh
copy of the original native base and imports the same archive; it does not
reuse the damaged tree.

That fresh `shadow` run passes all **1,424 imported file hashes**, using the
same payload, kernel and emulator binary. The monitor confirms shadow mode.
It then reaches a distinct module rejection while starting `fftr`, before
desktop startup. Shadow mode is the controlled workaround for this cycle;
the full-cache data discrepancy remains unresolved.

## MIPS IV interpreter admission

The 6.5.30 n32 libc also serves as the ELF interpreter and carries MIPS IV
flags `0x30000022`. The existing module only accepts the corresponding MIPS III
interpreter flags. This explains `Cannot execute ELF binary` despite a correct
file checksum. The main `fftr` and 4Dwm executables still carry MIPS III flags.

NetBSD `xiri` commit `93a258077244ea6e6a1a43a9d2e8b8fa41aa6555` admits this
n32 interpreter only when NetBSD reports a
MIPS IV CPU. R4400 still rejects it. Existing ABI, ELF layout and segment
permission checks remain in place. No native kernel replacement is needed.
The [admission regression](../../lab/irix-mips4/check-admission.py) compiles the
actual module validator against both donors' ELF headers and program headers:
the new 6.5.30/MIPS IV case fails before the change and all 20 cases pass after
it, including MIPS III rejection and malformed-input checks. The module also
passes its cross-build, kernel export and relocation audit.

The import probe's `--module-build` option verifies the candidate and matching
kernel hashes, installs into a private disk overlay, halts cleanly and cold
boots before testing. It verifies filesystem module loading at securelevel 1,
and records the effective module separately from the inherited base image.
It cannot be combined with a native package that would supply another module.

Both release guests pass that cold-boot module check and their 55-file native
ledger. The R5000 guest then re-verifies all 1,424 vendor files, successfully
runs the 6.5.30 `fftr` compiler, opens the core desktop and File Manager, and
passes the shell/HOME checks plus desktop relogin. The R4400 guest passes its
6.5.22 import, filetypes, first desktop/shell, File Manager and logout checks.

Those two longer runs were interrupted by host SIGTERM before completing
their final session checks. Their raw results retain `failed` / `Interrupted
by signal 15`; both halt cleanly with the base unchanged. In the R5000 run the
signal interrupted a quoted serial command, so its input was cancelled before
resending normal shutdown. The probe now cancels incomplete input before
collecting failure diagnostics. This was not a measured application failure.

Shorter follow-up runs reuse each private, halted disk. `--reset-filetypes`
first checks the saved original `desktop.otr` against the imported manifest,
then restores it on the disposable copy and removes its generated state file.
The full vendor ledger is checked again, and activation rebuilds the table.
An already-installed candidate still needs a cold boot, exact native/module
hashes, `modstat` and securelevel checks; it simply avoids a redundant second
boot. No failed run is reclassified as passing.

The complete 6.5.22 repeat now passes, including relogin, native ctwm and clean
shutdown; see its [raw result](2026-11-14-mips4-6.5.22.json). A second R5000
run again verifies every vendor file and reaches its desktop, then receives
host SIGTERM. Its diagnostics are collected normally and it halts cleanly.
The external signal's sender is not identified by these records.

A separately labelled `--desktop-only` follow-up references that full-import
result and checkpoint by hash, rechecks the native ledger and ten core vendor
files, and repeats the desktop sequence after another cold boot. It uses an
explicitly tracked host process with a captured exit status. It does not
repeat or replace the full-import checksum evidence.

That [focused 6.5.30 run](2026-11-14-mips4-6.5.30.json) now passes with host
exit status zero and a verified clean halt. It references the
[interrupted full import](2026-11-14-r5000-import.json), which retains its
failed status despite passing every vendor checksum before the interruption.
The combined evidence establishes:

Native-account acceptance uses the UID-filtered `pgrep` check and the X window
tree. The raw process-list diagnostic is empty because those executed probes
used `ps -u`; the maintained diagnostic now uses NetBSD's `ps -U` selector.

O2 and Octane first require native NetBSD boot/driver/board work, as explicitly
recorded in the [platform roadmap](../ROADMAP.md#milestone-5-indigo2-and-octane-expansion).

```sh
python3 scripts/probe-irix-import.py \
  --bundle .work/images/xiri-netbsd-desktop-20261114-controls \
  --payload .work/imports/irix-6.5.30f-v1 \
  --cpu r5000 \
  --emulator-bundle .work/emulators/iris-xiri-20261114-r5k-config \
  --output .work/irix-6.5.30-r5000-fixed
```

For the shadow-cache candidate run, also specify `--cache shadow` and
`--module-build .work/irix-mips4-module`, with a new output directory. A cleanly
halted import may be copied with `--resume-import`; all vendor file hashes
are checked again before execution.

The output directory must be new. The emulator override verifies both binary
hashes against its manifest; it does not repin the 6.5.22 manual image.

The cycle fetched IRIS upstream `5fb831ce7057a8978759ae57b151d631a448d1e7`
on November 14 and again on November 15, already included in `xiri`; no merge
or emulator rebuild was required. All 83 host
tests pass with their required local sockets enabled. The first sandboxed
invocation could not create the sockets used by three archive-transfer tests;
the unrestricted local test run passes without source changes.

Cleanup retains the two final private disk states, the small module build,
donors/payloads and compact verification evidence. Obsolete test disks,
duplicate media, compiler intermediates and monitor bytecode were removed:
about **4.52 GiB of allocated file footprint**. Reflink sharing means this is
not a measurement of exclusive physical space recovered. The final host
process check finds no running IRIS or import probes. No qualified manual
image, donor, pinned worktree or unrelated project was removed.
