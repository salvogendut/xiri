# Indirect OpenGL on the two Indy desktops

SGI Clock and the Background colour browser exposed the same NetBSD graphics
stack. The 6.5.22f R4400 and 6.5.30f R5000 v4 images use Xorg 1.10.6 and
NetBSD 11.0/sgimips Mesa (reported as 19.1.17 by the renderer). In an indirect GLX session, Xorg
receives the client's OpenGL requests and Mesa renders them inside the
server process.

## What failed

The stock Clock traces from both Indys resolve to the GLX Render dispatcher
and Mesa's `_mesa_Viewport`, `viewport` and `clamp_viewport`. The earlier
Background trace reaches `_mesa_MatrixMode` through the same dispatcher.
The function names come from the matching NetBSD release debug files.
The stripped binaries had attributed several frames to nearby exported
symbols. The signed release manifest and the binaries' debug-link CRCs
identify the source and debug sets used for the comparison.
[Clock and font tests](2026-11-24-indy-link-clock-xosview.md) ·
[Background test](2026-11-06-desktop-colours.md)

Two parts of the server build matter.

1. The old Xorg exports its own GL API setters and stores the current
   context and dispatch table in process-global variables. Mesa's
   software renderer reads its current context from thread-local storage
   in shared `libglapi.so.1`. A context bound through Xorg's setter is
   consequently invisible to that renderer.
2. The 408 fixed OpenGL function slots agree. All 362 extension slots in the
   legacy table either moved or have no corresponding Mesa entry.
   Binding both sides to the same GL API alone left native `glxinfo`
   entering an unrelated Mesa function. The old GLX sources already have
   a dispatch-remapping mode. The sgimips build uses it to look up extension
   slots by name from the same Mesa definitions that built the provider.
   The build checks the fixed slots and rejects a missing extension used
   by a compiled GLX source.

The source changes are confined to the old X server build in
`external/mit/xorg/server/xorg-server.old` in the NetBSD fork.
The server executable and its loadable GLX module need a matching build.
Clock also needs the release's own SGI Font Manager map and indexed Iris
bitmap fonts. Both Overlay 1 font maps had SHA256
`ad312e4fe00a89c1f642c131e510250e27b01f83d327afb1c92680ae175154a2`.
The guest kernel, Newport driver and IRIX application binaries
are the existing v4 versions. [NetBSD fork change](https://github.com/salvogendut/NetBSD-xiri/commit/df8a46a636f0d95bf73b9b45a9312bcb112ec105)

## Results on the v4 test copies

| Authenticated 4Dwm session | Native indirect rendering | Original SGI Clock |
| --- | --- | --- |
| 6.5.22f, R4400 | GLX 1.4, softpipe, animated three-colour gears | [Clock screenshot](2026-11-24-indy-glx-6.5.22f-clock.png) |
| 6.5.30f, R5000 | GLX 1.4, softpipe, animated three-colour gears | [Clock screenshot](2026-11-24-indy-glx-6.5.30f-clock.png) |

Each Clock opened its own 100×100 window of class `Clock` alongside the
ordinary desktop `XClock`. Both redrew at 220×220. Two dumps of each resized
window had the same byte count and different checksums. In the framebuffer,
the moving hands changed 1,458 pixels inside the R4400 clock face and 2,352
inside the R5000 face. The independent native gears test also reported
multiple frames on both guests.

Opening the Solid colour browser in GL mode while SGI Clock was running
exhausted both 256 MB guests' swap. Both NetBSD kernels logged that they
killed Xorg. This is a separate failure from the original signal 11.
Mesa's softpipe context constructor reserves 6 shader stages × 128 sampler
views × 16 tiles × 32×32 RGBA floats, or **192 MiB of texture-cache payload
per context**, before bookkeeping. The release debug data confirms 768
cache objects of 262,336 bytes each, totalling 201,474,048 bytes. The
initializer touches every tile's address. Resident memory depends on page
use and allocation history.

We repeated the picker test on fresh desktops with SGI Clock closed. Both
started with 32,736 KiB of unused swap. On the R5000, Xorg grew from
21,944 KiB resident and 57,040 KiB virtual to 168,144 KiB resident and
437,312 KiB virtual at the recorded sample. Both kernels subsequently logged
`Xorg ... killed: out of swap`. The shipped `Background*useGl: False`
selects the working X11 controls.

## Build and delivery

For the v4 userland, build from clean objects with NetBSD 11.0 `src` and
`xsrc`, taking the sgimips changes to the old X server build from the
NetBSD fork. The release source for the graphics stack is in NetBSD's
[11.0 X sources](https://ftp.netbsd.org/pub/NetBSD/NetBSD-11.0/source/sets/xsrc.tgz).
The pair tested here is available locally in
`.work/native/netbsd-sgimips-glx-20261124/`.

| Guest path | SHA256 |
| --- | --- |
| `/usr/X11R7/bin/Xorg` | `860032d8f89f1301f189280091493d529a9f794c636c96d15cf0806a58ad76bc` |
| `/usr/X11R7/lib/modules/extensions/libglx.so.0` | `c276e620c2555f4d2094ac61518dfb8aac28200d111fd4dbeb528aa7c45e5370` |

Both objects link to `libglapi.so.1`. Xvfb and Xnest also cross-linked.
An independent comparison verified all 408 core and 362 extension mappings.
The generator rejected a mismatched core slot and an unavailable extension
referenced by a test source. All 94 Xiri host tests passed.

The published v4 images still ship the stock Xorg and their original font
profiles. Packaging the pair and the matching vendor fonts is a separate
release step. IRIS `xiri` at `39ef6dff` already contained upstream
`057ba095` when fetched for this cycle.
